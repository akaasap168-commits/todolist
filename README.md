# Daily Planner

紙のウィークリープランナー（`プランナー/3_WeeklyPlanner.tex`）をデジタル化した、ToDo リスト兼デイリー/ウィークリープランナーです。

- **週ビュー**: 紙と同じレイアウト。Daily Priorities、Weekly Priorities / Micro Success / Weekly Evaluation、7 日分のタイムライン。
- **日ビュー**: 1 日を大きく表示。スマホではこちらが既定。
- **Vision | Real**: 15 分刻みで「理想の予定」と「実際にしたこと」を並べて記録。予定どおり率を自動計算。
- **ToDo**: 今日 / 期限あり / いつか / 完了。タイムラインや Daily Priorities にドラッグして予定化。
- **Google カレンダー**: 予定の取り込み表示と、Vision の書き出し。
- **検索**: 過去の Vision / Real / ToDo / 振り返りを横断検索。
- **同期**: Firebase（Firestore）でリアルタイム同期。オフラインでも使え、復帰時に同期。
- **PWA**: ホーム画面に追加してアプリのように起動。

公開 URL: https://akaasap168-commits.github.io/todolist/

## 使い方のコツ

| 操作 | 方法 |
| --- | --- |
| 予定を作る | タイムラインの空き部分をドラッグ（クリックだと 30 分） |
| 移動・長さ変更 | ブロックをドラッグ / 上下の端を引っ張る |
| 予定どおりにできた | Vision ブロックを開いて「✓ 予定どおり実施」 |
| 今やっていることを記録 | 「▶ 今から記録」→ 終わったら「■ 記録終了」 |
| ToDo を予定にする | ToDo をタイムラインにドラッグ |

## セットアップ

[SETUP.md](SETUP.md) を参照してください。設定しなくてもローカル保存モードで使えます。

```

## 構築の記録（何をしたか・用語解説つき）

このアプリを「自分の PC で動かせる状態」から「インターネット上で公開され、複数端末で同期し、Google カレンダーと連携する状態」にするまでに行った作業の記録です。太字の IT 用語には、その場で解説を付けています。

### 全体像

```
 [自分の PC]                [GitHub]                        [Google]
  C:\todolist   ── push ──▶  リポジトリ (Public)
                              │ GitHub Actions が自動で
                              │ テスト → ビルド → デプロイ
                              ▼
                             GitHub Pages ──────────────▶  Firebase Authentication（ログイン）
                             （公開 URL）                   Cloud Firestore（データ保存）
                                  ▲                         Google Calendar API（予定の読み書き）
                            ブラウザで開く

### 1. リポジトリのクローン

- **リポジトリ（Repository）**: ソースコードと、その変更履歴一式を入れておく保管場所。GitHub 上にあるものを「リモートリポジトリ」、手元の PC にあるものを「ローカルリポジトリ」と呼ぶ。
- **Git**: ファイルの変更履歴を記録・管理するツール。「いつ・誰が・何を変えたか」を後から追える。
- **GitHub**: Git のリポジトリをインターネット上で保管・共有するサービス。
- **クローン（clone）**: リモートリポジトリを丸ごと手元にコピーすること。

`git clone https://github.com/akaasap168-commits/todolist.git` で `C:\todolist` に複製しました。

### 2. Firebase プロジェクトの作成（SETUP.md 1-1〜1-4）

- **Firebase**: Google が提供する、アプリの裏側（サーバー機能）をまとめて借りられるサービス。自分でサーバーを用意・管理しなくてよい。この仕組みを **BaaS（Backend as a Service）** と呼ぶ。
- **フロントエンド / バックエンド**: 画面に表示されてユーザーが操作する部分がフロントエンド、データの保存や認証などを裏で担う部分がバックエンド。本アプリはフロントエンドを GitHub Pages、バックエンドを Firebase が担当する。
- **Spark プラン**: Firebase の無料プラン。個人利用の範囲では課金されない。

|---|---|---|

### 3. 環境変数の設定

- **環境変数**: プログラム本体に直接書かず、外から渡す設定値。環境（手元の開発用 / 公開用）ごとに値を差し替えられる。
- **`.env` ファイル**: ローカル開発用の環境変数を書くファイル。`.gitignore` に登録済みのため Git には記録されない。
- **`.gitignore`**: Git に記録させないファイルを指定するリスト。

手元の `.env` に Firebase の設定値 6 つ（`VITE_FIREBASE_*`）と、後述の `VITE_GOOGLE_CLIENT_ID` を記入しました。先頭の `VITE_` は、ビルドツール Vite がこの値をアプリに埋め込む対象として扱うための目印です。

### 4. GitHub への設定登録とデプロイ（SETUP.md 1-5）

- **ビルド（build）**: 開発用のソースコード（TypeScript など）を、ブラウザがそのまま読める形（HTML / JavaScript）に変換・まとめる作業。
- **デプロイ（deploy）**: ビルドしたものを公開サーバーに配置し、利用可能にすること。
- **GitHub Pages**: GitHub リポジトリから静的な Web サイトを無料で公開できる機能。公開 URL は https://akaasap168-commits.github.io/todolist/
- **GitHub Actions**: リポジトリで何かが起きた時（push など）に、決められた処理を GitHub のサーバー上で自動実行する機能。
- **ワークフロー（workflow）**: Actions で実行する処理の手順書。本リポジトリでは `.github/workflows/deploy.yml`。
- **CI/CD**: 変更のたびに自動でテスト・ビルド（CI: 継続的インテグレーション）し、自動で公開まで行う（CD: 継続的デリバリー / デプロイ）開発の仕組み。本リポジトリのワークフローがまさにこれ。
- **Repository variables（リポジトリ変数）**: Actions から参照できる設定値。ビルド時に環境変数として渡される。

行ったこと：

1. GitHub の Settings > Secrets and variables > Actions > **Variables** に Firebase の設定値 6 つを登録
2. deploy ワークフローを手動実行（`workflow_dispatch`）→ テスト → ビルド → GitHub Pages へのデプロイが成功

`deploy.yml` の流れ：

```
npm ci（依存パッケージを lock ファイル通りに導入）
  → npm test（自動テスト）
  → npm run build（Variables を埋め込んでビルド）
  → GitHub Pages へデプロイ
```

> **Secrets ではなく Variables を使った理由**: Firebase の設定値はビルド後の JavaScript に埋め込まれ、公開サイトから誰でも読める値です。暗号化して隠す Secrets を使っても意味がないため、公開前提の Variables に登録しています。

### 6. Google カレンダー連携（SETUP.md 2-1〜2-4）

- **API（Application Programming Interface）**: あるサービスの機能を、別のプログラムから呼び出すための窓口。ここでは Google Calendar API を使い、アプリから予定を読み書きする。
- **API 連携**: 自分のアプリから外部サービスの API を呼び出して機能を組み合わせること。
- **Google Cloud コンソール**: Google の API や認証設定を管理する画面。Firebase プロジェクトは同名の Google Cloud プロジェクトと一体になっている。
- **OAuth 2.0**: パスワードを渡さずに「このアプリに、自分のカレンダーへのアクセスを許可する」を実現する仕組み。ユーザーが同意画面で許可すると、アプリは期限付きの **アクセストークン**（一時的な通行証）を受け取る。
- **OAuth 同意画面**: 「このアプリが〇〇へのアクセスを求めています」と表示される確認画面。
- **スコープ（scope）**: アクセストークンで許可する操作の範囲。本アプリは `calendar.readonly`（予定の読み取り）と `calendar.events`（予定の作成・変更）の 2 つ。
- **OAuth クライアント ID**: Google に対して「どのアプリからの要求か」を示す識別子。
- **承認済みの JavaScript 生成元（オリジン）**: そのクライアント ID を使ってよい Web サイトの URL。ここに無いサイトからの要求は Google が拒否する。

### 7. セキュリティの考え方

リポジトリも公開サイトも **Public（誰でも見られる状態）** ですが、次の理由で安全に運用できる設計になっています。

- **公開されている値は「鍵」ではなく「住所」**: `apiKey` や `projectId`、OAuth クライアント ID は「どのプロジェクト宛か」を示す識別子で、知っていてもデータにはアクセスできません。Firebase の Web アプリでは、これらは必ずブラウザに配信される公開前提の値です。
- **守っているのはサーバー側のセキュリティルール**: 判定は Google のサーバーで行われ、ブラウザ側のコードを改ざんしても回避できません。UID は Google が署名したトークンから取り出されるため偽装できません。
- **UID の公開も問題なし**: UID はメールアドレスと同じ「識別子」であり、知っていてもその人になりすますことはできません。
- **秘密情報は含まれていない**: Git の全履歴を検索し、`.env`・秘密鍵・アクセストークン類が記録されていないことを確認済み。
- **非公開にしない理由**: ビルド済みのコードは公開サイトから誰でも読めるため、リポジトリを隠しても安全性はほぼ上がりません。また無料プランでは非公開リポジトリで GitHub Pages を使えません。

残るリスクと対策：

| リスク | 対策 |
|---|---|
| Google アカウントの乗っ取り（最重要） | Google アカウントの **2 段階認証（2FA）** を有効にする |
| GitHub アカウントの乗っ取り（悪意あるコードを push される） | GitHub アカウントの 2 段階認証を有効にする |
| `firestore.rules` を編集しても Firebase に反映されない | ルールを変えたら必ず Firebase コンソールに貼り付けて「公開」する |
| 依存パッケージの汚染 | `package-lock.json` でバージョンを固定済み。むやみに更新しない |

> **ログインは「安全の担保」ではなく「名乗り」**: ログインは「誰か」を確定させるだけで、「何を触れるか」を決めているのはセキュリティルールです。ルールが正しいことが安全性の本体です。
